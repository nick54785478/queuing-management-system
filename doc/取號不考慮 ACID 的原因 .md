# 系統架構決策說明：排隊系統取號機制為何放棄 RDBMS ACID 特性？

在設計高併發排隊系統（Queueing System）的取號機制時，我們刻意避開了關聯式資料庫（RDBMS）完整的 ACID 特性。這是一個經過精密計算的**架構取捨（Trade-off）**，我們透過犧牲部分的持久性（Durability）與強一致性（Strong Consistency），來換取系統在極高併發下的存活率與吞吐量。

以下是取號階段不依賴 RDBMS ACID 的三個核心原因：

## 1. 效能瓶頸：ACID 的代價過於高昂

關聯式資料庫為了保證 ACID（尤其是強一致性與持久性），背後付出了巨大的系統資源代價。若在 RDBMS 中實作取號（例如執行 `UPDATE queue_counter SET num = num + 1`），會面臨以下致命的物理與設計瓶頸：

*   **行級鎖競爭 (Row-Level Lock Contention)：** 在瞬間湧入數萬個請求時，所有的執行緒（Thread）都會試圖爭搶同一筆計數器資料的 Row Lock。這會導致大量的請求在資料庫層排隊等待解鎖，引發嚴重的阻塞。
*   **連線池耗盡 (Connection Pool Exhaustion)：** 由於鎖的等待，資料庫連線無法快速釋放。伺服器（如 Spring Boot 的 HikariCP）的連線池會在幾秒內被抽乾，導致後續所有請求直接拋出 `ConnectionTimeoutException`，系統隨之崩潰。
*   **磁碟 I/O 延遲：** ACID 為了保證持久性，每一次的 Transaction 提交都必須等待 Write-Ahead Logging (WAL) 確實寫入磁碟（Disk Sync）。在海量吞吐的需求下，實體磁碟的 I/O 會立刻成為無法跨越的效能天花板。

## 2. Redis 提供輕量且滿足需求的「原子性 (Atomicity)」

我們並非完全放棄原子性，而是將其降級到「記憶體級別」，交由 Redis 處理。

*   **絕對序列化的執行機制：** Redis 的核心命令執行模型是**單執行緒（Single-threaded）**的。這意味著無論同一瞬間有多少個請求發送 `INCR` 指令，Redis 都會嚴格地將它們排成一直線依序執行，絕對不會出現 Race Condition（競爭條件）導致兩位使用者拿到同一個號碼的問題。
*   **Lua 腳本的封閉性：** 透過 Redis Lua Script，我們可以將「檢查總名額上限」與「執行 `INCR` 取號」打包成一個不可分割的操作。Redis 保證腳本執行期間不會被其他指令插隊，這完美滿足了排隊取號所需的原子性與隔離性（Isolation），且回應時間能維持在極速的次毫秒級。

## 3. 業務本質：號碼牌屬於「過渡性資料 (Ephemeral Data)」

架構設計必須回歸業務場景的容錯度，將昂貴的系統資源花在刀口上。

*   **號碼牌不等於最終訂單：** 「排隊號碼」的業務價值僅存在於使用者等待的那幾分鐘內。如果發生極端情況（例如 Redis 主節點崩潰且來不及同步到備援節點），導致極少數的排隊資料遺失，最壞的結果僅是「少數使用者需要重新整理頁面再取一次號」。這種情況雖然會影響體驗，但**絕對不會造成企業財務損失或資料庫錯亂**。
*   **將 ACID 留給最核心的資產：** 系統資源是有限的。我們把最昂貴的 RDBMS ACID 保證，完全保留給使用者**通過排隊後、真正進行扣款與扣除庫存的那個瞬間**。這落實了「邊界非同步限流，核心強一致處理」的架構黃金準則。

---

**結論：** 
在排隊系統的入口處，**「讓系統活下來並快速發出號碼牌」比「保證這組號碼在機房斷電後絕對不遺失」更為重要。** 因此，利用 Redis 的高吞吐量取代 RDBMS 的 ACID，是此場景下的最佳架構實踐。
