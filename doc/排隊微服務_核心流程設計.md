# 排隊微服務 (QMS) 核心流程設計 (DDD & 六角形架構)

本文件專注於**「排隊微服務本身」**的核心流程設計。
依照架構決策，排隊系統屬於邊界層，為了追求極致效能與極簡化，**不引入 CQRS 與 Event Sourcing**，但仍嚴格遵循工作區的 `AGENTS.md` 規範，落實 **DDD（領域驅動設計）**與**六角形架構 (Hexagonal Architecture)**。

---

## 1. 核心領域模型定義 (SaaS 多租戶架構)

為了支援 SaaS (Software as a Service) 模式，系統必須具備**多租戶 (Multi-Tenancy)** 與**多活動 (Multi-Activity)** 的隔離能力。
在排隊系統中，我們的核心 Aggregate Root 依然是 `Ticket` (號碼牌)，但其內部必須強綁定租戶與活動的上下文。
*   **Aggregate Root**: `Ticket`
*   **Value Objects (VO)**: `TenantId` (租戶識別), `ActivityId` (活動識別), `TicketId`, `TicketStatus` (QUEUING, DEQUEUED, TIMEOUT), `QueueToken`

---

## 2. 獲取號碼牌流程 (Enqueue)

使用者發起排隊請求，系統透過 Redis Lua Script 原子化發放號碼牌。

```mermaid
sequenceDiagram
    autonumber
    participant Client
    participant Ctrl as 表現層 (Controller)
    participant App as 應用層 (TicketApplicationService)
    participant RedisPort as 基礎設施層 (TicketRedisAdapter)
    participant Redis as Redis Server

    Client->>Ctrl: POST /tenants/{tenantId}/activities/{activityId}/tickets (EnqueueTicketResource)
    Ctrl->>Ctrl: Assembler 轉為 EnqueueTicketCommand (包含 TenantId 與 ActivityId)
    Ctrl->>App: 呼叫 EnqueueTicketUseCase
    App->>RedisPort: 呼叫 TicketRepositoryPort.enqueue()
    RedisPort->>Redis: 執行 Lua (依據 TenantId+ActivityId 隔離 Redis Key 進行 INCR 取號與 ZSET 排隊)
    Redis-->>RedisPort: 回傳 TicketNumber 與 Token
    RedisPort-->>App: 回傳 Ticket (Aggregate)
    App-->>Ctrl: 回傳 TicketEnqueuedResult (Dto)
    Ctrl-->>Client: Assembler 轉為 TicketEnqueuedResource
```

### 命名與分層約束對齊：
*   **Resource (In/Out)**: `EnqueueTicketResource`, `TicketEnqueuedResource`
*   **Command**: `EnqueueTicketCommand`
*   **UseCase (Inbound Port)**: `EnqueueTicketUseCase`
*   **Application Service**: `TicketApplicationService` (無 CQRS，統包處理)
*   **Outbound Port & Adapter**: `TicketRepositoryPort` 由 `TicketRedisAdapter` (宣告為 package-private) 實作。

## 3. 即時狀態同步與心跳續命 (SSE & Heartbeat)

前端透過 SSE 獲取當前叫號進度，並定時發送 Ping 維持 Token 的有效性。

```mermaid

    autonumber
    participant Client
    participant Ctrl as 表現層 (SSE Controller)
    participant App as 應用層 (TicketApplicationService)
    participant RedisPort as 基礎設施層 (TicketRedisAdapter)

    %% SSE 連線與狀態廣播
    rect rgb(240, 248, 255)
        Note over Client, RedisPort: 狀態同步 (Server-Sent Events)
        Client->>Ctrl: GET /tenants/{tenantId}/activities/{activityId}/tickets/stream (SyncTicketProgressResource)
        Ctrl->>Ctrl: 建立 WebFlux Flux 連線
        loop 每秒定時查詢
            Ctrl->>App: 呼叫 SyncTicketProgressUseCase
            App->>RedisPort: TicketRepositoryPort.getCurrentServingNumber()
            RedisPort-->>App: 回傳最新進度
            App-->>Ctrl: 回傳 TicketProgressGottenResult
            Ctrl-->>Client: 透過 Flux 推播 TicketProgressGottenResource
        end
    end

    %% 心跳機制
    rect rgb(255, 250, 240)
        Note over Client, RedisPort: 心跳續命 (Ping)
        Client->>Ctrl: PUT /tenants/{tenantId}/activities/{activityId}/tickets/heartbeat (PingTicketHeartbeatResource)
        Ctrl->>Ctrl: Assembler 轉為 PingTicketHeartbeatCommand
        Ctrl->>App: 呼叫 PingTicketHeartbeatUseCase
        App->>RedisPort: TicketRepositoryPort.extendTTL()
    end
```

## 4. 批次放行與事件觸發流程 (Dequeue & Publish)

排隊微服務的背景排程，根據後端量能，定時從 Redis 取出排隊名單，並發送放行事件至 Kafka。

```mermaid
sequenceDiagram
    autonumber
    participant Worker as 排程層 (Inbound Adapter)
    participant App as 應用層 (TicketApplicationService)
    participant RedisPort as 基礎設施 (TicketRedisAdapter)
    participant MQPort as 訊息發布 (TicketMessagePublisherAdapter)
    participant Kafka as Kafka Event Bus

    loop 依設定速率觸發 (如每秒 100 筆)
        Worker->>App: 呼叫 DequeueTicketUseCase
        App->>RedisPort: TicketRepositoryPort.dequeue(limit)
        
        rect rgb(255, 235, 238)
            Note over RedisPort: Redis 批量放行
            RedisPort->>RedisPort: 從 ZSET 取出指定數量的 Ticket
            RedisPort->>RedisPort: 更新已放行最大號碼
        end
        RedisPort-->>App: 回傳 List<Ticket>
        
        loop 針對每一張放行的號碼牌
            App->>App: ticket.dequeue() (更新領域狀態並產生 Event)
            App->>MQPort: TicketMessagePublisherPort.publish(TicketDequeuedEvent)
            MQPort->>Kafka: 投遞 TicketDequeuedEvent 授權事件
        end
    end
```

### 邊界設計細節 (SaaS 考量)：
*   **觸發點 (Inbound Adapter)**：Spring `@Scheduled` 背景排程（或分散式排程如 XXL-JOB）針對「不同的 Tenant 與 Activity」獨立執行 `DequeueTicketUseCase`，各自控制放行速率。
*   **Redis Key 隔離**：底層 Adapter 操作 Redis 時，所有 Key 皆須帶有前綴 `qms:tenant:{tenantId}:activity:{activityId}`，確保不同客戶（租戶）的排隊活動資料絕對物理隔離。
*   **領域事件發布 (攜帶租戶資訊)**：`Ticket` Aggregate 在呼叫 `dequeue()` 行為方法時產生 `TicketDequeuedEvent` (`N + Ved + Event`)。該事件**必須包含 `TenantId` 與 `ActivityId`**，隨後交由 `TicketMessagePublisherPort` 發送至 Kafka。
*   **動態路由或 Topic 隔離**：Kafka 可依據 TenantId 發送至不同的 Topic，或共用 Topic 但以 TenantId 作為 Partition Key，讓多租戶的後端核心系統能精準識別並消費屬於自己的授權事件。
